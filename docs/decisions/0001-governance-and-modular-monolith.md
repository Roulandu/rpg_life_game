# ADR-0001：模块化单体 + 质量棘轮 + 组合门禁

- 状态：已接受
- 日期：2026-10-26
- 关联：`AGENTS.md`、`docs/modules.yaml`、`docs/process/*`

## 背景

项目已能跑通完整赛季，但缺少工程约束：

- 提交信息无法说明范围、验证与回归风险。
- 模块边界靠自觉，`store`、`llm`、`ui` 存在较多跨层引用。
- 技术债没有门禁，最大文件 760 行。
- 文档只有产品路线，没有架构/功能/接口/数据模型文档。
- 未来要支持 Android 平板、iOS、微信小程序、Web，平台差异不能继续散落。

一次性大规模重构风险高、会阻塞功能开发；但继续放任会让多人协作成本快速上升。

## 决策

采用**模块化单体 + 质量棘轮 + 组合门禁**：

1. 保持单仓库、单构建，不引入运行时插件系统。
2. 用现有目录作为模块，`docs/modules.yaml` 作为唯一事实源，`check:boundaries` 冻结现有违规、禁止新增。
3. 现有超标文件进入技术债基线，只降不升；新代码按更严格阈值执行。
4. TDD 用“提交 RED/GREEN 证据 + test-impact + 覆盖率棘轮 + CI 全量”组合验证，不追求无法证明的形式主义。
5. 文档与代码同提交；`check:doc-sync` 校验结构、路径、生成文件和“改代码必须改文档或豁免”。
6. 提交信息六段式 + 机器可读 Trailer；commit-msg 与 CI 双重校验。
7. 多端只固化端口/适配器规则和能力矩阵，不提前实现。
8. 大文件拆分按触碰频率渐进进行，不设一次性重构截止日期。

## 备选方案

| 方案 | 优点 | 缺点 | 未选原因 |
|---|---|---|---|
| 立即全面重构 | 架构干净 | 风险高、阻塞功能、难 review | 当前阶段收益/风险不匹配 |
| 只写规范文档 | 成本低 | 模型/人都会漂移 | 无法防止技术债和文档腐化 |
| 引入重型框架/插件系统 | 扩展性强 | 过度设计、迁移成本高 | 当前没有真实多插件需求 |
| 全面变异测试/覆盖率硬卡 | 测试更强 | 慢、易误伤、维护成本高 | 先组合门禁，后续按需引入 |

## 后果

### 正面

- 新代码有明确依赖方向和模块归属。
- 技术债不再增长，触碰大文件时逐步下降。
- 提交和文档可追溯，多人协作冲突更早暴露。
- 门禁可被 CI 执行，不依赖“模型自觉”。

### 负面/代价

- 短期提交摩擦增加（六段模板、hooks）。
- 基线维护需要人工 review。
- 文档门禁只能保证结构，语义仍需 review。
- 现有大文件仍然存在，只是被冻结。

### 迁移/落地

分阶段：

1. 规则与模块清单。
2. 架构/功能文档。
3. 质量脚本与基线。
4. Git hooks 与 CI。
5. golden replay、存档守卫、覆盖率 floor。

## 验证

- `npm run check` 全绿。
- 坏提交（缺段、缺测试、缺文档、超标文件、跨模块违规）被拒绝。
- 连续修改同一文件时，基线不升高。
- `docs:build` 生成文件无漂移。
