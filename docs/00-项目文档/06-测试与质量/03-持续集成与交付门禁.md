# 持续集成与交付门禁

CI 的唯一目标是：对**一个确定的 SHA**跑同一套本地可复现的检查，并留下可追溯的报告。仓库不假设一定存在 PR，也不包含自动部署。

## 触发矩阵

| 事件 | 触发条件 | 对比基线 |
|---|---|---|
| `push` 任意分支 | `branches: ['**']` | 分支推送按 `origin/main`；`main` 使用 `event.before` |
| `push` 标签 | `tags: ['v*']` | 从被验证 SHA 往前找最近标签；没有则用根提交 |
| `pull_request` | 任意目标分支 | `origin/<base_ref>`，并显式 `git fetch` |
| `workflow_dispatch` | 手动 | 输入 `base`；留空走下方默认规则 |
| `schedule` | 每周一 02:00（北京时间） | 默认分支的 `origin/main` |

`push` 与 `pull_request` 可能对同一提交各跑一次，这是可接受的重复；`concurrency` 按 workflow + ref 取消过期运行。

## 执行内容

```bash
npm run verify -- --full --base "$QUALITY_BASE"
```

步骤清单见 [质量门禁与例外规则](02-质量门禁与例外规则.md)。CI 不按路径过滤，不做“只跑改动测试”。

## 基线解析规则

1. 解析后必须执行 `git rev-parse --verify "$base^{commit}"`；不可达直接失败，禁止用空提交范围输出“检查通过”。
2. `main` 的 `event.before` 为全 0（新分支/强推）或不可达时，依次退到 `HEAD~1`、根提交。
3. `checkout` 必须 `fetch-depth: 0`；PR 额外 fetch 目标分支。
4. 脚本层同样校验：`resolveBase` / `mergeBase` / `commitsSince` 遇到不可达 ref 或 `rev-list` 失败会抛错。

## 报告与产物

每次运行写 `quality/reports/verify-<sha>[-dirty].json`，包含：

- `gitHead`、`dirty`、`branch`、`base`
- Node/npm 版本、GitHub run/ref/event
- 每个步骤的 `command`、`exitCode`、`status`、`durationMs`
- `result` 与失败原因

`status` 为 `passed` / `failed` / `not-run`；失败后未执行的步骤标 `not-run`，不会伪装成通过。若 `GITHUB_SHA` 与本地 `HEAD` 不一致，验证直接失败（防止验证对象漂移）。

CI 以 `if: always()` 上传 `quality/reports/` 与 `coverage/`，artifact 名称含 SHA 与 `run_attempt`，保留 14 天；同一条件写 Job Summary。摘要写入失败不会掩盖验证结论（`continue-on-error: true`）。

**artifact 会过期**。发布验收记录必须保存 run URL 与关键结果，不能只写 artifact 链接。

## 无 PR 验收路径

```text
本地 verify 绿 → 分支 push → 该 SHA 的 CI 绿 → 人工验收
→ 合入 main → main 上新 SHA 的 CI 绿 → 打 tag v* → tag 的 CI 绿 → 交付
```

- 没有 PR 也能完成验证；CI 在任意分支 push 时运行。
- 合入方式（merge / squash / rebase）产生**新 SHA** 时必须重新验证新 SHA，不能沿用旧 SHA 的结果。
- 标签只用于受控交付入口，不等于自动发布；本仓库没有自动部署。

## PR 与 fork

- PR 的 checkout 通常是 merge ref，验证的是合并结果，不是源分支 HEAD 本身；报告不能表述为“源分支 SHA 已通过”。
- fork PR 的 `GITHUB_SHA` 是 merge commit；需要确认源分支自身也跑过 CI 时，应查看源分支的 push 运行。

## 强制程度（当前事实）

- GitHub 分支保护、ruleset、必需状态检查属于**仓库管理员配置**，不能由仓库文件单独强制；本仓库不声称 main 已被保护。
- 当前受控交付入口是 `v*` 标签上的同一套 `verify`。是否在平台上把 CI 设为 required check，需要管理员在 GitHub 设置中确认。
- 定时任务只在默认分支生效，长期无活动后 GitHub 可能自动停用；它是巡检，不是强保证。
- 旧分支若缺少 `docs/00-项目文档/08-变更与治理/governance.yaml`，检查脚本会明确报“治理配置缺失”，不会静默跳过 CHG 校验；应先 rebase/合入 main。

## 本地命令

```bash
npm run verify -- --help
npm run verify -- --list
npm run verify -- --fast --base origin/main
npm run verify -- --full --base origin/main
gh run list --commit "$(git rev-parse HEAD)" --limit 1
gh run watch <run-id> --exit-status
```

本地通过不等于远端通过；未看到对应 run 的结论时，只能报告“CI 未出结果”。

## 未覆盖项

- 没有自动部署、自动打 tag、自动发布。
- 没有设备矩阵、真机 Android 构建、变异测试、端到端浏览器测试。
- 没有远端分支保护与必需检查的自动化配置。
