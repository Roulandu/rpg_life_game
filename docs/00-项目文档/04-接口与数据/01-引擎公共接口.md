# Engine 与世界接口

本文记录 `src/engine`、`src/world`、`src/domain` 中跨模块使用的公共函数。签名以代码为准；行为变化必须同步本文与对应功能文档。

## 调用约定

- **纯计算优先**：`advanceWeek`、`startDay`、`generateWorld`、`computeLeagueTable` 等接收输入、返回结果，不读写全局状态。
- **显式变更**：`applyDailyTraining`、`resolveEvent`、`resolveKeyMoment`、`playDay` 等会直接修改传入的 `WorldState`，调用方负责先 `structuredClone`。
- **确定性**：所有随机性通过 `createRng(seed, domain, ...parts)` 获得；同一输入必须得到同一输出。
- **无平台依赖**：这些函数不得 import UI、db、platform、llm、Capacitor 或 DOM API。
- **失败语义**：参数缺失/状态不一致时返回 `null` 或抛错；不会静默写半成品。

## 日回合

位于 `src/engine/day.ts`（快进与单日结算的唯一入口）与 `src/engine/dayContext.ts`（日维度 RNG/id）。

| 函数 | 签名 | 行为 |
|---|---|---|
| `startDay` | `(input: WorldState) => DayResult` | 克隆输入并就地走一天；需要玩家参与时停在开球并写 `pendingDayPlan`，时钟不动 |
| `advanceDay` | `(input: WorldState) => DayResult` | 同一天步进，但把停住的比赛按默认选项踢完；晨间步骤不会重跑（时钟仍钉在这天） |
| `advanceUntilDecision` | `(input: WorldState, limit: number) => FastForwardResult` | 一份克隆上连续走日，跳过平静日，停在第一件 `matchday / event / milestone`；`limit` 为空转兜底 |
| `playDay` | `(world: WorldState, options: { autoResolve: boolean }) => DayResult` | 内部原语：一天只结算一次，**就地修改**，只给快进与周适配器用 |
| `isPendingDay` | `(world) => boolean` | 时钟是否仍钉在未完成的一天（`pendingDayPlan` / live 报告 / 待处理回合） |
| `dayRng` | `(world, tag) => Rng` | `createRng(seed, tag, season, week, day)`：同标签逐日走不同随机流 |
| `dailyId` | `(world, prefix, suffix?) => string` | `<prefix>:<season>:<week>:<day>[:<suffix>]`：同周七天不撞键 |

`DayResult` / `FastForwardResult`：

```ts
interface DayResult {
  world: WorldState
  dayPlayed: number
  live: boolean
  quiet: boolean
  stopReason: 'matchday' | 'event' | 'milestone' | null
  match: MatchReport | null
  event: GameEvent | null
  seasonTransition: SeasonTransition | null
}

interface FastForwardResult {
  days: DayResult[]
  stopReason: 'matchday' | 'event' | 'milestone' | null
  quietDays: number
}
```

`days[*].world` 指向同一份对象，只有末项是最新状态；调用方只应使用 `fast.days.at(-1)`。

一天的顺序（`playDay`，不可交换）：`day === 1` 刷新用户俱乐部强度 → `advanceInjuries` → `accrueDailyFinance`（刷新周薪/开销口径 → 周薪与赞助、生活开销**加团队周薪**各按 1/7 挂进待入账 → 欠款按日罚士气）→ 训练日 `applyDailyTraining` → 活动日 `applyDailyAction` → 特训日 `applySpecialization` → `applyStaffDailyEffects`（教练席晨间三件事：士气托底、自信积累、伤停期间的体能维护）→ `expireEvents` → 今天有场次则 `startUserMatch`/`finalizeMatchday` → `simulateDayFixtures` → `day === 7` 时 `postWeeklyLedger`（两个累计器各取整一次、写**一条**周账流水并清零）紧接 `settleInvestmentsWeekly`（先逐笔结利息、再给波动品种漫步一次现值）→ `generateDailyEvents(world, 今天这场)` → `absoluteDay % 21 === 0` 时 `updatePlayerValue` → 时钟 +1 天（跨周/跨赛季时进位）→ 清空 `pendingDayPlan`。

## 周回合（日步进的适配器）

`src/engine/turn.ts` 保留同名同签名，内部把一周走成 7 次 `playDay`，让旧测试、golden 与非交互调用保持「一次推进一整周」的语义。

| 函数 | 签名 | 行为 |
|---|---|---|
| `startWeek` | `(input: WorldState, plan: WeeklyPlan) => TurnResult` | 写 `world.weekPlan = plan` 后逐日推进；停在开球时 `live = true` 且周次不变 |
| `completeWeek` | `(world: WorldState) => TurnResult` | 仅处理存在 `pendingDayPlan` 的那一天；仍有待处理回合时拒绝；否则自动踢完并走完剩余日子 |
| `advanceWeek` | `(input: WorldState, plan: WeeklyPlan) => TurnResult` | 兼容入口：`startWeek` + 自动处理关键回合 + `completeWeek` |
| `advanceWeeks` | `(world: WorldState, plan: WeeklyPlan, count: number) => TurnResult[]` | 连续推进整周，遇到退役或赛季切换提前停止 |
| `endSeason` | `(world: WorldState) => SeasonTransition` | 结算排名、奖项、奖金、声望、升降级、年龄、退役、合同、新赛季赛程；**原地修改** world |

`TurnResult`：

```ts
interface TurnResult {
  world: WorldState
  match: MatchReport | null
  event: GameEvent | null
  seasonTransition: SeasonTransition | null
  weekPlayed: number
  seasonPlayed: number
  live: boolean
}
```

「一次推进一周」的旧顺序（`src/engine/turn.ts`）现在等价于：`startWeek` 写 `weekPlan` → 七天 `playDay`（每天按上面的日顺序）→ 停在开球时保留 `pendingDayPlan` 且周次不变 → `completeWeek` 踢完那天并走完剩余日子。

`weekPlayed` / `seasonPlayed` 是“刚踢完的那一周”，不是推进后的周次。LLM 叙事必须使用这两个字段，否则会把新一周误写成已结束的一周。

叙事仍按周触发：store 只在**非 live 且周次跨过去**的一天结束后调用 `narrateTurn`，快进不会把它放大成每天一次。

## 比赛模拟

| 函数 | 签名 | 行为 |
|---|---|---|
| `determineUserSelection` | `(world, club, rng) => SelectionResult` | 根据能力差、教练信任、体能、状态、锐度与**教练打法契合度**决定首发/替补/不出场 |
| `selectionScore` | `(club, user, squadOverallWithoutUser, trust) => number` | 纯函数：入选评分的唯一算式，末项 `(styleFit − 0.5) × 4` 来自 `domain/coachStyle`，供选型与回归测试共用 |
| `startUserMatch` | `(world, fixture) => MatchReport` | 创建 live 报告：首发停在 0'，替补用 `advanceLiveMinute` 快进到登场分钟（与手点同一条路径，统计与事件为完整累积），初始化双方首发与全零统计；重复调用返回已有 live 报告 |
| `advanceLiveMinute` | `(world) => LiveMinuteResult \| null` | 每次只推进一步；返回分钟、球权、球位、持球人、传球轨迹、事件与 `paused / finished / halfTime`；关键回合分钟先按归属写入进攻三区球位并计控球再暂停；时钟跨过替补登场分钟时补一条幂等的 `sub` 事件 |
| `buildSpell` | `(input: SpellInput) => SpellResult` | 纯函数：Markov 控球连续、球位推进、1–3 段传球/带球轨迹、射门/进球判定；返回 `liveState` 供下一分钟与刷新恢复；`input.userEntryMinute`（缺省 0）让登场前的主角不被选成持球人 |
| `homePossessionShare` | `(home, away) => number` | 主队控球份额，按中场强度差修正并 clamp 到 0.3–0.7 |
| `kickoffState` / `momentState` / `goalState` | `(side) => MatchLiveState` | 中圈开球 / 关键回合进攻三区 / 进球门线 + `pendingKickoff` 三种画面状态 |
| `buildBeats` | `(input: BeatInput) => BeatResult` | 纯函数：调用 `buildSpell` 后生成该分钟射门/攻防事件与统计增量，不修改报告；进球分钟不重复计射门；`input.userEntryMinute`（缺省 0）是主角的分钟闸门，登场前的分钟不会把主角选成事件主体或持球人 |
| `advanceLiveMatch` | `(world) => MatchReport \| null` | 循环调用 `advanceLiveMinute` 直到下一关键回合分钟或 90 分钟；半场比分在 45 分钟后冻结 |
| `finalizeLiveMatch` | `(world) => MatchReport \| null` | 终场唯一结算入口：评分、赛季统计、MOTM、媒体、新闻、黄牌/伤病；幂等 |
| `simulateUserFixture` | `(world, fixture) => MatchReport` | 兼容包装：`startUserMatch` → 自动处理回合 → `finalizeMatchday` |
| `simulateBackgroundFixture` | `(world, fixture) => void` | 模拟其他比赛，写入比分与射手统计 |
| `simulateDayFixtures` | `(world) => MatchReport \| null` | 模拟**今天**其余比赛，写入比分与射手统计 |
| `getUserMatchFixture` | `(world, week?) => Fixture \| undefined` | 取用户本周赛程（周适配器与旧调用保留） |
| `getUserFixtureOnDay` | `(world, day?) => Fixture \| undefined` | 取用户某天赛程，缺省用 `world.day` |
| `opponentOf` | `(world, fixture) => Club \| undefined` | 取对手俱乐部 |

用户比赛从 `0-0` 开始逐分钟模拟：控球方以 0.64–0.83 的概率保持控球（中场强度差修正），球位在同侧控球时朝对方球门推进 0.04–0.18；进球概率为 `clamp(xG / 90 / 控球份额 × 势头, 0, 0.35)`，非进球分钟射门概率 0.12、射正率 38%。进球与射门共用同一持球人，`appendGoal` 唯一写入比分与射门统计。随机流为 `spell / move / chance / beat-actor / goal / pitch / pitch-lane / pitch-carrier`；势头由最近 10 分钟内已结算回合推导，不落盘，因此读档可重放。

## 关键回合

| 函数 | 签名 | 行为 |
|---|---|---|
| `generateKeyMoments` | `({ player, rng, minutes, isHome, startMinute?, opponents? }) => KeyMoment[]` | 根据出场时间生成 5–7 个关键回合（12 类、每回合 5 选项），`roll` 在生成时固定；`opponents` 决定每个选项读写哪三名对手，生成后概率不再变化 |
| `pendingKeyMoments` | `(world) => KeyMoment[]` | 尚未处理的回合 |
| `hasPendingKeyMoments` | `(world) => boolean` | 是否存在待处理回合 |
| `resolveKeyMoment` | `(world, momentId, optionId, options?: { advance?: boolean }) => MatchReport \| null` | 按固定 `roll` 与选项结算；只能处理下一个待处理回合。live 报告立即改写比分，`advance` 默认 `true`，为 `false` 时停在当前分钟；赛季数据留到终场 |
| `autoResolveKeyMoments` | `(world) => MatchReport \| null` | 对每个待处理回合选择默认（成功率最高）选项 |
| `finalizeMatchday` | `(world) => MatchReport \| null` | live 报告：推进到 90 分钟后调用 `finalizeLiveMatch`；旧版 `final` 报告：刷新媒体反应与新闻 |

不可变条件：

- `roll` 生成后不得重抽。
- 对手属性只能在 `generateKeyMoments` 之前读取并写死进选项，结算阶段不得重算概率。
- 必须按数组顺序处理，不能跳回合。
- 比分只通过 `appendGoal` 追加，不重算整场；live 回合的赛季进球/助攻/评分只在终场统计一次。
- `finalizeMatchday` / `finalizeLiveMatch` 在仍有未处理回合时返回 `null`，不得提前生成媒体反应。
- 终场结算幂等：`status === 'final'` 时直接返回，不重复统计或发布新闻。

### 关键回合概率（引擎内部）

`src/engine/data/scoreChance.ts` 与 `src/engine/matchOpponent.ts` 不进入 `src/engine` 公共入口，只被 `liveMatch`/`keyMomentGen` 与测试深引用。

| 函数 | 签名 | 行为 |
|---|---|---|
| `scoreChance` | `(player, input: ScoreChanceInput, opponents?: OpponentPair \| null) => { successChance, successBasisZh }` | `clamp(base + Σ actorCoef×我的属性 + Σ input.terms − Σ opponentCoef×对手属性, low, high)`，0.1% 粒度取整；无项可加时回落到 `flatBasisZh` |
| `buildOptionTable` | `(rows: OptionRow[], context: KindContext, kind: KeyMomentKind) => KeyMomentOption[]` | 把一类的选项表逐行套公式，产出恰好同样数量与顺序的选项；非常量行自动追加 `resolveMoveTerms` 给出的绝技与对手段 |
| `resolveOpponents` | `(world, source: { homeId, awayId, lineups? }) => OpponentPair \| null` | 从对面首发回查 `world.players`，给出 `keeper/marker/shooter`；同分取先出现者；无阵容返回 `null`；纯读取不消耗 RNG |

- `KindContext = { player, isHome, opponents? }` 是 12 类 builder 的唯一入参；`opponents` 缺失时选项退化为「只看自己属性」。
- 系数单位是「每 1 点属性对概率的贡献」，`0.0012` = 每点 0.12%，因此表里的数字可与依据文本直接对账。
- `low === high` 的常量选项既不吃属性也不挂绝技，保持「文案写死多少就是多少」。
- 绝技加成由 `domain/moveQueries.ts` 的 `resolveMoveTerms` 在这一步注入，公式本身不需要为某条绝技改；见下面的「绝技」。

## 事件

| 函数 | 签名 | 行为 |
|---|---|---|
| `expireEvents` | `(world) => void` | 把 `expiresDay` 早于当前绝对日的开放事件标记为 `expired`；旧档缺 `expiresDay` 时回落 `expiresWeek` 那一周的最后一天 |

| `scopeMatches` | `(scope, conditions) => boolean` | 合取求值，运算符只有 `eq / in / lt / lte / gte / between`；字段不在白名单则抛错 |
| `resolveEvent` | `(world, eventId, choiceId) => GameEvent \| null` | 应用选项效果、写结果文本、标记 `resolved`；无效/重复返回 `null` |
| `applyEffects` | `(world, effects, label?) => void` | 统一应用 `Effect[]`，写财务/关系/新闻等副作用；`exp` 只经 `grantExp` 入账，`learnMove` / `moveProgress` 转给名宿路径的闸门（见「绝技」），其余走状态与关系的 clamp 分支 |

已退役：`generateWeeklyEvent`（周日 72% 拍一条）。它的上下文 if/else 阶梯改成了数据包里的 `when` 条件，`match` 参数改为**当天的战报**，因此赛后事件落在比赛当天而不是下周日。

事件是“引擎事实 + 玩家选择”的组合；LLM 只能改写标题/正文，不能新增选项、改变效果或 `templateId`。模板内容在 `data/events/*.json`，由 `src/domain/eventContent.ts` 的 Zod 模式与 `assertWhitelist` 在加载时硬校验。

| `grantExp` | `(world, amount, reason: 'training' \| 'match' \| 'event' \| 'staff' \| 'specialization') => number` | 经验入账的唯一入口：负值与非整数先 `Math.max(0, Math.round(...))`，同一次 `exp` 与 `lifetimeExp` 一起涨；`reason` 是 `training` 或 `specialization` 时先乘私教 `expFactor`（最高 1.5），比赛与事件来源不打折也不加成；主角首次攒够 6 点且尚未投过时写一条当日新闻（`dailyId(world, 'news:exp', reason)`），之后不再重复播报 |
| `ratingToExp` | `({ rating, minutes, goals, assists }) => number` | 纯函数：`(rating − 6.5) × 8 × minutes / 90 + goals × 6 + assists × 4`，评分 ≥7.8 另加 4，未出场或差评截 0 |
| `investAttribute` | `(world, attrKey, points) => InvestOutcome` | 就地修改世界：八道闸门依次为无主角 / 非正整数点数 / 比赛中（`pendingDayPlan` 或 live 报告）/ 位置闸门 / 点数档位（`attrInvestment[key] + points ≤ attributeCap`）/ 属性值天花板（`attributes[key] + points ≤ INVEST_HARD_CAP`）/ 潜力闸门 / 经验不足；前两道上限同回 `overCap`。任一不过就整笔拒绝并回 `InvestReject` 码，不做部分成交 |
| `TRAINING_EXP` | `Record<TrainingFocus, number>` | 训练课每次的经验产出（恢复课 1 点，其余 2 点） |
| `investmentCost` / `investmentSeriesCost` | `(invested) => number` / `(invested, points) => number` | 纯算式：`6 + 2k` 递增单价与连投总价；UI 显示与引擎扣费共用，引擎侧扣费再经私教折扣 `×(1 − investDiscount)`（最低仍付 1 点） |
| `attributeCap` | `(player) => number` | `min(96, 40 + floor(lifetimeExp / 20))`，随累计经验解锁；管的是这一项**累计可投多少点**，不是属性值能练到多少（属性值天花板是 `INVEST_HARD_CAP`） |
| `canInvestAttribute` | `(attrKey, position) => boolean` | 十项属性都可投，仅 `goalkeeping` 需要 `positionGroup === 'GK'` |
| `fitsPotential` | `(player, attrKey, points) => boolean` | 抬高后的 `computeOverall ≤ potential` |
| `maxInvestable` | `(player, attrKey) => number` | 同时受「买得起 / 练得到上限 / 不越过潜力」三条约束的最大点数 |
| `allocationBudget` / `checkAllocation` / `applyAllocation` | 见 `src/domain/allocation.ts` | 建号点买：预算 `(age − 16) × 3 + 4`（青训 +3）、单项 ≤ +4、总和 ≤ 预算、加完不越过潜力；非法问题以 `AllocationIssue[]` 返回 |
| `investExp` | `(attrKey, points) => Promise<InvestOutcome \| null>` | store 侧唯一动作（`src/store/growthSlice.ts`）：`structuredClone` → `investAttribute` → 落盘 → `notice`/`error` |

`grantExp` 只 import `dayContext` 与 `domain`，不 import `day.ts`；比赛进行中判定读 `world.pendingDayPlan` 与 `world.lastMatch.status`，避免 `day → training → growth → day` 的循环依赖。

## 随机数与哈希

> 位置：`src/lib/rng.ts`（原 `src/engine/rng.ts`）。随机数与哈希是平台无关的纯函数，下沉到 `lib` 供 `engine`/`world`/`db` 共用，不再造成 `world→engine`、`db→engine` 依赖与 `engine↔world` 循环。

| 函数 | 签名 | 用途 |
|---|---|---|
| `createRng` | `(seed, ...parts: (string \| number)[]) => Rng` | 按 seed + 域 + 参数创建独立随机流 |
| `Rng.next/float/int/chance/pick/shuffle/weighted/normal/poisson` | 见 `src/lib/rng.ts` | 所有随机行为的唯一入口 |
| `hashString` | `(input: string) => string` | 存档 checksum、golden 哈希 |
| `stableStringify` | `(value) => string` | 稳定序列化 |
| `hashState` | `(value) => string` | 状态哈希 |
| `seededId` | `(seed, ...parts) => string` | 确定性 ID |

不同业务域必须使用不同的 `parts`，避免新增逻辑改变旧随机流。例如 `createRng(seed, 'match', fixture.id)` 与 `createRng(seed, 'event', world.season, world.week)` 相互独立。

按天执行的步骤（训练与伤病、每日新闻、事件选项副作用）走 `dayRng(world, tag)` 与 `dailyId(world, prefix)`（`src/engine/dayContext.ts`，域尾追加 `season/week/day`）——id 不带日会让同周七天撞键，新闻与副作用记录因此互相覆盖。事件 id 同样带日段（`event:<season>:<week>:<day>:<templateId>`），掷骰用 `dayRng(world, 'event')`。仍按周拍的一步继续用 `season/week` 作键：投资账本的价值漫步取 `createRng(seed, 'market', investmentId, season, week)`，因为一只持仓一周只该被踢一脚——按日建域会让同一笔钱一周波动七次，而中途另存的存档再接着踢就会出现两条轨迹。持仓 id 反过来必须带日（`dailyId(world, 'inv', kind)` → `inv:<season>:<week>:<day>:<kind>`），否则同一周买两笔活期会撞键；余额告急新闻也从「每周一条」改成按日打 id（`news:finance:debt:<season>:<week>:<day>`），靠每 28 个绝对日一次的条件控制频率。`Fixture.id` 保持 `fixture:<leagueId>:<season>:<week>:<index>`：它同时是比赛随机盐，日粒度改造不得改其结构。个人团队的招聘池走**赛季域** `createRng(seed, 'staff-pool', season, role)`（`src/domain/staff.ts`）：既不带周也不带日，所以同一季里反复打开 `/staff` 看到的是同一批人，换季才换人；它也不写进存档，因此这条流不会与比赛、事件的随机流相互挤位。

| `deleteSave` | `(id) => Promise<void>` | 删除并清理 `lastSaveId` |
| `exportWorld` | `(world) => string` | 生成带 checksum 的 JSON（`saveVersion` 取 `CURRENT_SAVE_VERSION`，当前 12） |
| `importWorld` | `(text) => WorldState` | 校验原始 checksum 后迁移到当前版本；不落库 |

`downloadWorld`（`(world) => Promise<FileExportResult>`）已从 `db/repository` 迁到 `store/exportSave`，经 `platform/fileExport.exportTextFile` 落地：原生分支写 `Directory.Cache` 后交给系统分享面板，Web 分支触发浏览器下载；结论用判别式联合表达，调用方按 `ok` / `reason` 决定提示是成功、轻提示还是错误。

## 错误与兼容

- `generateWorld` 缺少可用俱乐部时抛错。
- `startUserMatch` / `simulateUserFixture` 缺少球员/俱乐部时抛错。
- `resolveEvent` / `resolveKeyMoment` 对无效输入返回 `null`，由 store 转成中文提示。
- `loadWorld` / `importWorld` 使用 Zod 校验，错误信息包含字段路径；旧版本存档先迁移，checksum 始终在迁移前校验。
- 接口签名变化必须同步本文、功能文档与调用方；破坏性变化需要 ADR。

## Golden 回放

- `quality/golden/season-seed-42.json` 记录 seed 42 赛季回放的 `engineVersion` 与最终状态哈希。
- 连续控球、球位推进、射门/进球同源、球场位置模型与存档 v4 都改变过引擎输出，因此 `ENGINE_VERSION` 一路升到 `0.4.1`。
- 存档 v5 把结算粒度从周改成天（训练/伤病/新闻按天执行、强度重算与身价评估改拍、比赛按日命中），引擎输出必然变化，因此 `ENGINE_VERSION` 升到 `0.5.0` 并重算 golden。

- 存档 v9 给每个球员补 `moves: []`、给周计划补 `specialization: null`，这两个字段参与 `hashState`，因此 `ENGINE_VERSION` 升到 `0.10.0`，基准 `c43d95700e96f860` → `d3170bbf49ce3b2f`。绝技层本身不消耗随机数，新生成的世界没人持有绝技，`resolveMoveTerms` 返回空数组，关键回合概率与 0.9.0 同源。
- 比赛表现掉落（`grantMoveDrops` 在终场往 `user.moves` 写进度并可能插新闻）把基准推到 `0.11.0` / `d3170bbf49ce3b2f` → `82fe56a7e245ea77`；它用独立 RNG 域 `moveDrop`，不动其他步骤的随机流。
- 名宿批次把基准推到 `0.12.0` / `82fe56a7e245ea77` → `a53d784da26c391d`：`generateWorld` 多一条 `rel:legend:${playerId}` 关系，事件池多注册 mentor 包 9 条模板（权重 28），`rng.weighted` 的候选集与权重分布随之改变。
- 存档 v11 给 `Finance` 补 `pendingIncome / pendingExpenses / investments` 三个键，`hashState` 覆盖整个 world，因此结构本身就位移：实测这一步把 `a53d784da26c391d` 变成 `41c1aa6857d93818`。之后的两笔行为提交（周日整周结算改「日累计 + 周日取整」、投资利息与漫步）在同一份 v11 结构上复跑回放仍得 `41c1aa6857d93818`——前者终局金额与旧口径相同（改的是可读的中间态，不是结果），后者在回放里没有任何开仓入口所以空转。基准停到 `0.13.0` / `3b40c1fbe0ca642b`，差值纯粹来自 `ENGINE_VERSION` 字符串本身（把常量临时回退 0.12.0 复跑得回 `41c1aa6857d93818`）。
- 存档 v12 给世界顶层补 `staff: []`（个人团队名册），`staff` 参与 `hashState` 所以结构本身位移：实测把 `3b40c1fbe0ca642b` 变成 `0515c620b8b5f310`。教练席的三处挂钩在这条回放里全部取恒等值——回放用固定周计划 `extra: 'none'`，引擎侧没有任何雇佣入口，跑完整季 `world.staff.length === 0`（临时脚本实测，脚本未提交），所以队医的伤停折算、心理咨询师的士气下限与关键回合 `psychBonus`、私教的经验/投资/特训系数一步都没被触发。基准停在 `0.14.0` / `0977f1c7baccb177`，`0515c620b8b5f310 → 0977f1c7baccb177` 的差值纯粹来自 `ENGINE_VERSION` 字符串本身。
- 真机反馈整改把基准推到 `0.15.0` / `0977f1c7baccb177` → `a5df29729457cf02`：主角分钟闸门下沉到 `domain/matchMinutes`，`buildSpell`/`buildBeats`/`buildPitchFrame`/`carrierPlayer` 四处持球人与射手选取都受闸门约束，`rollUserMatchEvents` 的事件分钟与登场窗口取交集，`scoreChance` 的主角项统一一位小数——前三项改变了随机数的**取用对象**而不是抽取次数，最后一项只改文本。存档结构不变，`CURRENT_SAVE_VERSION` 保持 12。
- 真机反馈整改第二批把同一条 `0.15.0` 基准再推到 `a5df29729457cf02` → `5c8603ff2effd2cf`：`draftUserBase` 的随机材料去掉 `options.name`，改为 `createRng(seed, 'user', age, position)`。姓名原本参与 `'user'` 域抽签，而该域的 rng 会交回给后续生成步骤继续消费，所以去掉它位移的是整条世界生成流而不只是十项属性。存档结构不变，`CURRENT_SAVE_VERSION` 保持 12。
- 基线由 `npm run quality:golden` 重新生成；脚本连续跑两次确认同 hash 后才写入。
- 修改任何影响引擎输出的规则时，必须评估是否需要升 `ENGINE_VERSION` 并更新回放；哈希变化而版本未升会被 `check-anti-regression` 拦截。
- 事件内容不参与接口签名：`data/events/*.json` 扩容只改 `world.events[*].choices` 的内容，因此接口文档里事件相关条目见 `docs/00-项目文档/03-功能设计/01-功能规则与流程/03-每日事件.md`，本文件只在引擎语义变化时升版本。
