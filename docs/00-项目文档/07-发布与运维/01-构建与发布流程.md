# 构建与发布流程

本仓库只负责**构建与验证**；发布、签名、上架和部署都需要人工执行。没有自动部署、自动打 tag 或自动发布流水线。

## Web 构建

```bash
npm ci
npm run verify -- --full --base origin/main
npm run build
```

产物在 `dist/`。Vite 使用 `vite-plugin-pwa` 生成 Service Worker；构建失败或验证未通过时不得发布。

## Android 构建

环境：JDK 21、Android SDK（`ANDROID_HOME` 已设置）、Node 22+。

```bash
npm install
npm run android:sync      # 以 native 模式构建 Web 资源，并同步到 android/
cd android
./gradlew assembleDebug    # Windows: gradlew.bat assembleDebug
```

产物：`android/app/build/outputs/apk/debug/app-debug.apk`。

说明：

- `npm run build:native` 使用 Vite 的 `native` mode，`vite-plugin-pwa` 在该模式下禁用，Service Worker 不会注册。Android 包由 Capacitor WebView 加载本地资源，不需要离线缓存层。
- `androidScheme: 'https'`：WebView 的来源是 `https://localhost`，与浏览器一致。
- 状态栏、启动屏、键盘和返回键已经接入；返回键在主页会先存档再退出，其余页面回退历史。
- 调试包未签名，只用于本机安装。正式发布前需要配置签名、版本号和隐私声明；这是当前的人工缺口。
- 如果 Gradle 首次构建需要下载依赖，请保持网络连接；国内网络可按需配置镜像。

### Android 打包前置体检：npm run android:doctor

```bash
npm run android:doctor             # 逐条 ✔/⚠/✖，出现 ✖ 时退出码 1
npm run android:doctor -- --json   # 连探针原始数据一起输出，供脚本消费
```

判定口径写在纯函数 `scripts/quality/lib/device.ts`（由 `tests/quality/device.test.ts` 的 7 条用例守住），`scripts/quality/check-device.ts` 只负责采集探针与打印结论：

| 项 | 级别 | 口径 |
|---|---|---|
| `ANDROID_HOME` / `ANDROID_SDK_ROOT` | ✖ 不通过 | 未设置或目录不存在时，Gradle 与 adb 都无从定位 |
| `adb` | ✖ 不通过 | SDK 的 `platform-tools` 里没有可执行的 adb |
| 在线设备 | ⚠ 提醒 | `adb devices -l` 只认 `state=device`；没设备时构建照跑，真机清单跑不了 |
| `dist/index.html` | ✖ 不通过 | 缺失说明还没构建 Web 负载，先 `npm run build` |
| `assets/public/index.html` | ✖ 不通过 | 缺失说明从没同步过，跑 `npm run android:sync` |
| 负载一致性 | ✖ 不通过 | 比对两份 `index.html` 的 SHA-256；`index.html` 内嵌本次构建的资源哈希，「dist 新、assets 旧」一定会暴露 |
| debug APK | ⚠ 提醒 | 没有 APK 提示 `assembleDebug`；APK 的 mtime 早于负载 mtime 提示重打包 |

**为什么要有这条命令**：2026-11-03 体检时 `app-debug.apk` 与 `android/app/src/main/assets/public/` 都停在 10-25，而 `dist/` 早已走在 v11/v12 存档、财务与个人团队之后——装到手机上的仍是旧界面，且当时没有任何命令会报告这件事。补跑 `npm run android:sync` 与 `./gradlew.bat assembleDebug` 后，新 APK 为 4,852,026 字节（11-03 23:34），体检除「无在线设备」外全绿。

- `android:doctor` 不进 `verify` 步骤：它依赖本机 SDK、adb 与设备在场，属于打包与真机验收前的手动门禁，联网/CI 门禁不能替它判定。
- 真机验收清单与结论口径见 [跨平台开发规范](../05-开发规范/04-跨平台开发规范.md)。

## 发布候选检查单

发布候选必须是一个**确定的 SHA**，并且在该 SHA 上完成：

- [ ] `npm run verify -- --full --base <上一发布点>` 通过，报告位于 `quality/reports/`。
- [ ] CI 对该 SHA 的运行通过；记录 run URL，不以本地结果代替远端结论。
- [ ] `npm run build` 与 `npm run android:sync`（如需 Android）成功。
- [ ] 要出 Android 包时先 `npm run android:doctor`（出现 ✖ 必须先修），`assembleDebug` 后再跑一次确认 APK 不早于 WebView 负载。
- [ ] 存档版本有变化时，旧档 fixture、迁移与导出/导入往返测试通过（见 [数据迁移与回滚方案](02-数据迁移与回滚方案.md)）。
- [ ] 手机宽度（360–390px）与桌面宽度手动验收关键流程；设备在场时按 [跨平台开发规范](../05-开发规范/04-跨平台开发规范.md) 的真机验收清单逐条记录。
- [ ] 无密钥、Token、真实个人信息进入仓库。
- [ ] 在 `08-变更与治理/02-验证记录/` 写 `VER-...`，记录被验证 SHA、命令结果与 CI run。

## 打标签

```bash
git tag -a v0.1.0 -m "v0.1.0"
git push origin v0.1.0
```

- 打 tag 需要明确授权；本仓库流程不会自动创建或推送标签。
- tag `v*` 会触发与分支相同的 `verify`。tag 的 CI 结果才是该版本的受控交付证据。
- 合入 main 或打 tag 若产生新 SHA，必须重新验证新 SHA，不能沿用旧 SHA 结果。
- 发布后补全 `VER` 记录的 CI run 与验证结论；artifact 会过期，run URL 是长期证据。

## 回滚与失败处理

- 发布前失败：停止交付，修复后在**新提交**上重新走检查单。
- 发布后发现问题：按 [数据迁移与回滚方案](02-数据迁移与回滚方案.md) 恢复备份或回退到上一版本，再做前向修复。
- 不使用强制推送改写已发布历史；不删除已发布的 tag 作为常规回滚手段。
