# 数据迁移与回滚方案

存档结构以 [数据模型与存储设计](../04-接口与数据/03-数据模型与存储设计.md) 为准；本文只写迁移前后的操作与回滚原则，不复制迁移表。

## 基本原则

- 版本**只升不降**：`CURRENT_SAVE_VERSION` 只增不减，旧客户端拒绝读取更高版本存档。
- 迁移只前进，且必须幂等；重复执行不应改变结果。
- 迁移失败时**拒绝导入/加载**，不能写入半成品或部分字段。
- 迁移不依赖当前引擎运行结果，不消耗 RNG，不改变未声明的时钟与待处理回合。
- 任何存档结构变化都必须：升版本、写迁移、保留旧版本 fixture、加导出/导入往返测试。

## 变更前

1. 导出并保留一份当前版本的真实存档（用户数据、测试 fixture 各一份）。
2. 在 `tests/db/` 保留旧版本 fixture；不要用迁移后的数据反向构造旧档。
3. 确认迁移步骤注册在 `src/db/migrateSteps.ts` 的 `MIGRATION_STEPS`，且有测试覆盖。
4. 更新数据模型文档的迁移表与兼容性说明。
5. 在 CHG 的“兼容与回滚”写明：旧档能否继续、是否提示用户、失败表现。

## 验证

```bash
npm run test:coverage
npm run quality:anti-regression -- --base origin/main
```

必须覆盖：

- 旧版本 fixture 能迁移到当前版本并继续游玩。
- 导入导出往返后深度相等。
- `saveVersion` 高于当前版本时被拒绝。
- checksum 不匹配时被拒绝。
- 迁移幂等：重复执行结果相同。

## 回滚

回滚不是反向迁移。可行手段按优先级：

1. **恢复备份**：用升级前导出的存档恢复用户数据。
2. **回退应用版本**：安装上一版本；旧客户端可能无法读取新版本存档，因此必须先确认备份可用。
3. **前向修复**：保持新版本，修复迁移缺陷并发布新版本；已写入的新结构不倒退。

禁止：

- 写“降级迁移”把新结构改回旧结构。
- 删除用户存档或静默重置进度。
- 通过删除测试或跳过校验让失败迁移“通过”。

- [ ] 迁移表、fixture、往返测试齐全。
- [ ] `CURRENT_SAVE_VERSION` 与 `world.version` 的升级理由清楚。
- [ ] 回滚路径已写入 CHG 与 VER。
- [ ] 发布说明提示用户升级前导出存档。
