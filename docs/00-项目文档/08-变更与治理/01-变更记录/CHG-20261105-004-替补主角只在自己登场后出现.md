## 背景与目标

真机试玩反馈的问题 4、6、7、11、12，五个现象共用同一条根因链。

1. **问题 11（主角登场前就出现在文字直播里）**：`matchGoals.ts` 的进球闸门（`userWeight` 要求 `minute >= userEntryMinute`）本身是对的，但 `carrierId` 这条链路**短路了它**：
   `liveSpell.pickCarrier`（FWD/MID 池含主角，无分钟闸门）→ `steps[].carrierId` → `matchBeats.carrierActor`（carrier 优先命中，不校验分钟）→ `liveMinute.carrierPlayer`（只校验「在不在 lineups」）→ `scoreGoal` 里 `carrierPlayer(...) ?? pickScorer(...)`，`??` 右侧那个正确的闸门永远走不到。
   构造侧的成因是 `domain/lineup.ts` 的 `forcePlayerId`：只要 `userPlayed` 就把主角塞进**首发 11 人**，于是 `lineups` 里始终有主角，「在不在 lineups」这个判据天然为真。
   既有测试 `liveMatch.test.ts` 的「替补登场前不会成为进球者」为真，只是因为那条用例恰好落到 `pickScorer` 分支 —— 覆盖率假象，本批要连带记录。
2. **问题 12（比赛应从登场分钟开始播，而不是先预告）**：`createLiveReport` 从 0 分钟开始，主角第 70 分钟才登场，玩家要手点 70 次才能看到自己的比赛；`LiveMatchStage.tsx` 只能靠一行「你将在第 N 分钟登场」把空档解释过去。
3. **问题 4（踢到 72' 刷新后回到 11'）**：`liveSlice.tickLiveMatch` 与 `jumpToNextKeyMoment` 只 `set` 不 `persist`，刷新后 `resumedPlayback` 只能重放到「最近一次已落盘的关键回合结算点」。不是数据损坏，是播放进度从未落盘。
4. **问题 6（同一人同一分钟两个阵营徽标）**：`matchBeats.saveLine` 把事件 `side` 设成 `otherSide(side)`（门将一方），文案里的 `{player}` 却是射门者。
5. **问题 7（「传球 52.911」）**：`engine/data/scoreChance.ts` 的对手项用了 `round1`，主角项是裸插 `${value}`，两种小数位并存。

目标：登场分钟成为**单一真相源**，六处持球人/参与者选取都受同一闸门约束；实时比赛从登场分钟开始播；播放进度按节流落盘；两处文案口径统一。

本次不做：不动 `save.schema.ts`（`CURRENT_SAVE_VERSION` 仍为 12）；不给 `MatchLineupPlayer`/`MatchReport` 增加登场分钟字段；不把 `applyDailyAction` 改成每日执行；不重排 `beatTexts.ts` 语料库；不做问题 13/14 的数值调整（另立 CHG）。

## 验收条件

- `domain/matchMinutes.ts` 提供 `userEntryMinuteOf`（首发 0 / 替补 `90 - userMinutes` / 未出场 90）与 `onPitchAt`；`liveMinute.ts`、`liveMatch.ts`、`LiveMatchStage.tsx` 的内联重算全部替换为该 helper。
- 主角登场前（`minute < entry`）的任一分钟内：`buildSpell` 不产出主角 `carrierId`、`buildBeats` 不产出 `isUser` 事件、`buildPitchFrame` 不把球画在主角脚下、`advanceLiveMinute` 不产生主角进球/助攻。
- `userStarted` 与未出场主角的行为逐字节不变（首发 `entry = 0`，闸门为恒真；`userPlayed = false` 时主角不在 lineups 内）。
- `startUserMatch` 对替补场次在返回前确定性推进到登场分钟：调用与玩家手点完全相同的 `advanceLiveMinute`，累计控球分钟恰为登场分钟，且与逐分钟手播的终场报告哈希一致。
- 登场分钟产生一条 `type: 'sub'` 事件（幂等，刷新重放不重复），实时时间轴与赛后战报都能显示。
- 播放中按节流写库：每 5 分钟、比分或事件数变化、暂停、终场各触发一次；关键回合结算与「完成比赛」仍然各只写一次。
- `saveLine` 的 `side` 与文案主体同侧（射门方），并在 `matchBeats.test.ts` 钉住。
- `scoreChance` 的主角项与对手项都用 `round1`。
- 测试数量不下降；`npm run verify -- --fast` 全绿；`ENGINE_VERSION` 升 `0.14.0 → 0.15.0` 后 golden 重跑通过。

## 方案与取舍

- **登场分钟是派生值而不是新字段**：它 100% 由 `userPlayed / userStarted / userMinutes` 决定。加字段等于造第二套真相，而且一旦为此动 `save.schema.ts` 就要 12→13 + 迁移 + 旧档 fixture + 往返测试。闸门放在**使用侧**，lineup 的职责仍然只是「谁在这队的首发 11 人里」。
- **闸门用可选数字 `userEntryMinute`（默认 0）而不是 `{ id, entryMinute } | null`**：`MatchLineupPlayer.isUser` 已经存在，`PitchFrameInput` 拿不到 `world.playerId`，用数字 + `isUser` 判据能让 domain 层与 engine 层共用同一个原语，也避免在 `BeatInput` 里嵌套对象。
- **快进复用 `advanceLiveMinute`，不改成「报告起点 = 登场分钟」**：`report.stats` 按 1..N 逐分钟累计，跳过前段会让替补出场的控球率凭空偏低，与同场快速模拟不可比；事件历史缺前段等于「凭空从第 70 分钟开始」；`pendingKickoff` 与半场采集都读 `currentMinute`，起点漂移就是改比赛结构。RNG 安全性：`createRng(seed, scope, fixtureId, minute)` 按分钟独立取键，「何时抽」不影响「抽出什么」，快进在数学上不漂移 —— 这条由等价性测试钉住。
- **`sub` 事件在时钟走到登场分钟时追加，不在建报告时追加**：`liveMatch.test.ts` 的 `expectLiveConsistency` 断言 `events.every(e => e.minute <= currentMinute)`，建报告时就写入会让实时报告显示尚未发生的事件。幂等用 `events.some(e => e.type === 'sub')` 判断，刷新重放不会重复。
- **`rollUserMatchEvents` 用「抽完再上钳 `Math.max(entry, drawn)`」**：保持 RNG 抽取次数与顺序完全不变 ⇒ 首发（`entry = 0`）行为逐字节不变；若改为缩小 `rng.int` 区间，会同时改变首发的抽值分布。
- **参数从 5 降到 4**：`rollUserMatchEvents(world, user, goals, assists, rng)` 已经贴着「参数 ≤5」的上限，再要窗口只能收 `report`。`goals/assists` 本来就取自 `report.userGoals/userAssists`。
- **节流落库而不是每 tick 落库**：Dexie 每次写入都要序列化整个 `WorldState`，500ms 一次会让播放本身被 IO 拖慢；每 5 分钟 + 状态变化点的写入，把刷新回退上限压到 5 分钟以内。
- **重新定基线一条既有测试**：`livePlayback.test.ts` 的「播放中 tick 不写库」钉的是「实现机制 = 零写入」，而这个机制正是数据丢失的成因，它不是不变量。保留该 `it`（测试数不减少），把断言升级为节流契约。
- **不在 `matchFinalize.settleUser` 之后二次追加 `sub` 事件**（与批准计划的偏差）：grep 确认 `createLiveReport` 只有一个生产者，快速模拟同样经 `advanceLiveMinute` 走到 `simulateMinute`，所以实时与快速模拟都已经被覆盖；再加一次调用只会多一个「时钟已越过登场分钟就不再补」的边界，属于无生产路径的防御代码。

## 防回归

新增/改造的契约（按现象归组）：

- **闸门本身**：`tests/domain/matchMinutes.test.ts` 钉住「首发 0 / 替补 `90 - userMinutes` / 未出场 90」与「非主角不受闸门影响」。
- **六处选取全部受闸门约束**：`tests/engine/substituteGate.test.ts` 的 `回归: 替补登场前的分钟里出现主角持球与射门文本` 专门构造「carrier 已经是主角」的用例打穿短路，覆盖 `liveSpell.pickCarrier`、`matchBeats.pickActor`、`matchBeats.carrierActor`、`liveMinute.carrierPlayer` 四条分支；`回归: 球场帧在主角登场前把球画在他脚下` 覆盖 UI 侧独立 rng 的 `domain/pitch.ts`；`回归: 主角的黄牌与受伤事件落在登场窗口内` 覆盖 `matchUser.rollUserMatchEvents`。
- **回落分支**：`tests/fixtures/substituteMatch.ts::soleAttackerLineups` 把主角同侧非门将全改成 `CB`，让「攻击池为空 ⇒ 回落到全量池」成为确定性判据；这条是上次漏掉 `pool = attackers.length > 0 ? attackers : players` 的原因。
- **快进等价性**（本项目最重要的确定性契约）：`回归: 快进到登场分钟与逐分钟模拟的累计统计完全一致` + `回归: 实时比赛从主角登场分钟开始播，而不是从 0 分钟空转`。
- **`sub` 事件幂等**：`回归: 替补登场时战报里有一条且只有一条登场事件`、`首发与未出场都不产生登场事件`。
- **节流落库**：`tests/store/livePlaybackPersist.test.ts` 逐 tick 比对「该不该写」与「实际写了几次」，并验证刷新后重放到终场的报告哈希一致。
- **首发零回归**：既有 `tests/engine/liveMatch.test.ts`、`liveMinute.test.ts`、`tests/store/livePlayback.test.ts` 全量保持绿，闸门默认 `entry = 0` 时恒真。

### 覆盖率假象（同类问题排查记录）

`tests/engine/liveMatch.test.ts` 原有的「替补登场前不会成为进球者」在缺陷存在时仍然为绿 —— 那条用例恰好落到 `pickScorer` 分支，而缺陷在 `carrierId` 短路分支。教训：**断言「某个结果不出现」时必须确认它经过了哪条生产分支**，否则闸门形同未测。

`tests/fixtures/liveStore.ts` 的 `vi.mock('../../src/db')` 只在该 fixture 被求值时注册。若测试文件先 `import { useGameStore }` 再 import 该 fixture，`src/store/helpers.ts` 会绑到真实的 `saveWorld`，`saveWorldMock.mock.calls.length` 恒为 0。`tests/store/livePlaybackPersist.test.ts` 已把该 fixture 置于首行并加注释说明；`tests/store/livePlayback.test.ts`、`tests/store/matchdayStore.test.ts` 原本就是这个顺序。

## 技术债与例外

- **阈值事实修正（需要人决策的项，登记但不越权改配置）**：`quality/oxlint-tech-debt.json` 写了 `overrides` 让 `tests/**` 放宽到 600 行 / 函数 100 行 / 复杂度 20，但 `oxlint` 实际对 `tests/**` 仍按 `max-lines 300 / max-lines-per-function 60 / complexity 12` 报警，`check-tech-debt` 因此把超线的测试判成「新增」技术债。本批不调基线、不改配置，而是按实际阈值拆分：`tests/engine/substituteGate.test.ts` 拆成 3 个 `describe` 并抽出 `replayStatsTo`，`tests/store/livePlayback.test.ts` 把 tick 落库用例迁到新建的 `tests/store/livePlaybackPersist.test.ts`，`tests/engine/scoreChance.test.ts` 的新用例独立成 `describe`，`src/store/liveSlice.ts` 的 `jumpToNextKeyMoment` 抽出 `jumpFrames`（复杂度 13 → ≤12）。overrides 是否真要生效属独立治理项，未在本批处理。
