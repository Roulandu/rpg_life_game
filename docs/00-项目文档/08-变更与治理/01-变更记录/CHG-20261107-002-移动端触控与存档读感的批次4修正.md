## 背景与目标

2026-11-06 三赛季真机实测（问题清单第 16–22 条）留下的最后一批：手机上点不中、看不懂、存不下。

1. **契合度显示成「6161%」**：`src/ui/screens/team/PlayerStyleCard.tsx:25` 给 `StatBar` 同时传了 `value=61` 与 `hint='61%'`，而 `StatBar` 本来就打印 `value`（`src/ui/components/StatBar.tsx:27-30`），于是数字被写了两遍。`hint` 的设计用途是**单位后缀**，不是重复数值。
2. **种子框是个没有上界的数字输入**：`CareerStartCards.tsx:54` 只做 `Math.max(1, Number(v) || 1)`。实测输入 21 位数字会被 JS 静默折成 `1e+21`，`rollSeed()` 给的是 100000–999999 的六位种子（`useCareerDraft.ts:15-17`），而校验和 `createRng` 都能吃下任意数——两个明显不同的种子（如 `1e21` 与 `1000000000000000000000`）会生成同一个世界；小数与空串同样静默改写。
3. **360/390px 上有一批点不中的目标**：主页头部的设置图标宽约 33px（`DashboardHeader.tsx:55` 只有 `px-2`），建号页「随机」是 `chip`（高约 24px，`CareerStartCards.tsx:42`），设置页「显示 Key」宽约 31px（`ApiKeyFields.tsx:28`），三条数据按钮 `py-3` 实测约 40px 高（`LocalDataSection.tsx:23,34,43`）。现有契约里，高度只查主页区块，宽度只在标题页渲染（`tests/ui/touchSizeContract.test.tsx`），所以这四处一直是盲区。
4. **标题页装饰层把页面横向拖出 42px**：`TitleScreen.tsx:15` 的 `app-shell` 与 `src/styles.css` 的 `.app-shell` 都没有 `overflow-hidden`，`title-grid` 里的宽内容能把视口撑开。
5. **导入同一个文件会攒出一串同名同周期的存档**：`careerSlice.ts:176` 一律 `createSaveId(world)`（`save:${seed}:${Date.now()}:${Math.random()}`），导出文件里又不带 saveId（`save.schema.ts:177` 的 `saveEnvelopeSchema` 没有这个字段），所以「导入→删不掉、认不出、也盖不回原来那份」。摘要表 `SaveSummary`（`src/domain/saveTypes.ts`）里没有种子与创建时间，两行看上去完全一样。
6. **存档越玩越大**：`prepareNextSeason`（`src/engine/season.ts:215-232`）只把上一季的事件标 `expired`、把新赛季赛程合并进来，从不删除任何东西。实测 2.2MB（第 1 季第 2 周）→ 7.1MB（第 3 季第 35 周），其中 `fixtures` 2.3MB、`players` 1.0MB；引擎每天一次 `structuredClone(world)` + IndexedDB 全量写，体积直接换算成手感。

目标：手机上每个可点目标 ≥44px 且横向不溢出；种子输入按它宣称的口径校验；导入能覆盖、列表能分辨；跨季不再无限堆积死数据。

## 验收条件

1. `StatBar` 的契合度只显示一次数值（`61%`），`hint` 只用于单位后缀；其他 `StatBar` 调用点不变。
2. 种子输入只接受 `1–999999` 的整数：非法（空、`0`、负数、小数、>999999、`1e21`）时给出中文提示且不写回草稿；合法时按整数写回。`rollSeed()` 与校验后的取值域一致。
3. 主页头部图标按钮、建号「随机」、设置「显示 Key」与三条数据按钮在 360/390px 下 ≥44×44px；标题页在 360px 下横向溢出为 0（`scrollWidth - clientWidth === 0`）。
4. 导出文件带上来源 saveId；导入时该 id 已存在 → 原位覆盖同一份存档，不存在或旧文件不带 id → 仍然新建，绝不覆盖别人的档。
5. 存档列表行能分辨两份同周期存档：摘要带种子与创建时间并显示出来。摘要属派生投影，不升存档版本。
6. 跨季清理：进入新赛季后，已结束赛季的 `fixtures` 与该赛季已过期的 `events` 不再留在存档里；当季数据一条不少，历史与奖项仍读得到。
7. 第 6 条属于存档结构语义变化：`CURRENT_SAVE_VERSION` 12 → 13，迁移幂等（重复跑不产生差异），旧 v12 档导入→迁移→导出→再导入往返一致，并有 v12 fixture。
8. 快进一次最多 9 天（`src/store/daySlice.ts:19`）属产品手感，本批不擅改，登记技术债。
9. 测试只增不减；`npm run verify -- --fast`、提交后 `npm run verify -- --full --base <推送前 SHA>`、远端 CI 全部出结论。

## 方案与取舍

**清理放在 `prepareNextSeason`，不放在存档层。** 体积的来源是「引擎自己攒出来且明确不再使用」的数据；让 db 去猜哪些赛程算过期会把玩法口径搬进存储层。判定用 `season < world.season` 与 `status === 'expired'`，两者都是引擎已经写好的事实。

**迁移只删「回不去」的东西，且必须幂等。** v13 迁移对老档做同一件事：删掉早于当前赛季的赛程与已过期事件。跑第二次没有可删，因此重复导入不会继续变化。历史（`world.history`）与赛季摘要不动，奖杯页与时间线照旧读得到。

**导入覆盖只在「文件里写明了来源 id 且这个 id 确实存在」时发生。** 其余一律新建，绝不因为 id 撞上就抹掉别人的生涯——宁可多一条存档，不可丢一条。旧导出文件没有 `saveId`，走新建路径，行为与今天一致。

**摘要加字段不升存档版本。** `summarizeWorld` 每次写入与读取都从 `record.world` 重算，落盘的 `summary` 从来不是事实源（`12-存档与导入导出.md`「存档 ID 与摘要」已写明），所以列表要区分两份同周期存档只需加投影字段。
