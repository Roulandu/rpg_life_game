# 变更与治理说明

本目录把“规则、证据、例外”做成可检查的文件，避免只靠口头约定或 Agent 记忆。

## 唯一配置源

`governance.yaml` 定义：

- `effectiveFrom`：从哪一天起强制检查；更早作者日期的历史提交不追溯判红。
- `changeRecordDir` / `verificationRecordDir`：记录目录。
- `requiredTypes`：必须关联变更记录的提交类型（当前为 `feat / fix / refactor / perf`）。
- `levels`：`standard` 与 `light` 两档必备章节。

`docs / chore / test` 提交可以豁免 CHG；如果写了 `变更记录:` Trailer，仍会校验 ID 与记录是否存在。

## 变更记录 CHG

文件名：`CHG-YYYYMMDD-NNN-中文标题.md`。

- `NNN` 在当天唯一；文件名前缀必须等于 frontmatter `id`。
- frontmatter 至少包含 `id / title / type / status / level / created / updated / scope / commits / verification`。
- `created` 日期必须与 `id` 中的日期一致。
- `feat / fix / refactor / perf` 只能使用 `level: standard`；`docs / chore / test` 可用 `light`。

### 生命周期

| 状态 | 含义 | 检查强度 |
|---|---|---|
| `draft` | 进行中 | 只要求 ID、文件名、frontmatter 与章节标题存在 |
| `verified` | 本地必需检查完成，CI 可待执行 | 所有章节必须有实质内容；`验证证据` 至少一条命令或“不适用及理由” |
| `accepted` | CI 已绿且已合入/交付 | 额外要求 `验收结论` 非空且 `ciRun` 有值 |
| `superseded` | 被后续记录取代 | 保留历史；不要求 `ciRun` |

### 证据与 SHA

- 本地记录不要预填“记录自身所在提交”的 SHA，也不要把 `HEAD` 写成已验证结果。
- 本地阶段写 `HEAD` 与 dirty 状态、命令和输出摘要；CI 通过后补 run URL/run id。
- 只有 `accepted` 才要求 `ciRun`；未推送时写“CI 待推送”，不得写“CI 通过”。
- merge/squash 产生新 SHA 时必须重新验证新 SHA，不能沿用旧 SHA 的 CI 结果。

## 验证记录 VER

`VER-YYYYMMDD-NNN-中文标题.md` 只用于发布候选 / tag 验收，不要求每次变更都写。

- `status: passed | failed | partial`。
- `passed` 必须填写被验证的 `sha`（7–40 位十六进制）与 `ciRun`。
- artifact 会过期；发布记录必须写 run URL 与关键结果，不能只留 artifact 链接。

## 规则例外 EXC

`04-规则例外记录.md` 登记需要人决策的例外（范围、原因、风险、替代验证、责任人、复查条件）。它不是自动门禁：例外必须在对应 CHG 中同步说明，并接受 review。

## 命令

```bash
npm run quality:change-records
npm run quality:commit-msg -- <message-file>
npm run quality:commit-range -- --base origin/main
npm run verify -- --help
```
