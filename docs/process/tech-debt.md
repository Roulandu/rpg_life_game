# 技术债与棘轮

## 原则

技术债只能**局部冻结、逐步下降**，不能因为“这次赶进度”继续增长。现有大文件不要求一次拆完，但每次修改都必须让它不变大。

## 阈值

新代码（`src/**`）：

| 指标 | 阈值 |
|---|---|
| 单文件行数 | ≤300 |
| 单函数行数 | ≤60 |
| 圈复杂度 | ≤12 |
| 嵌套深度 | ≤4 |
| 参数个数 | ≤5 |
| 嵌套回调 | ≤3 |
| 单函数语句数 | ≤50 |
| 单文件重复率 | ≤3% |

测试（`tests/**`）适当放宽：文件 ≤600、函数 ≤100、复杂度 ≤20、语句 ≤80，但同样禁止 `.only` 和无理由 `.skip`。

阈值配置在 `quality/oxlint-tech-debt.json`，重复率配置在 `quality/jscpd.json`。

## 为什么是这些数

- 300 行：一个文件通常应只承载一个职责；超过后 review 和测试成本明显上升。
- 60 行：函数超过一屏很难整体理解；复杂逻辑应拆成命名清晰的步骤。
- 复杂度 12：超过后分支组合难以穷举测试。
- 参数 5：超过后建议用 options 对象，避免位置参数错配。
- 重复率 3%：允许少量必要重复，超过通常意味着应抽公共函数。

这些是工程经验值，不是绝对真理；调整阈值需要 ADR 或至少一次团队 review。

## 基线

`quality/tech-debt-baseline.json` 只记录当前**超标实体**的实际值，按实体 + 指标保存：

```json
{
  "version": 1,
  "tool": "oxlint",
  "entities": {
    "src/world/generator.ts": {
      "metrics": { "lines": { "value": 760, "max": 300 } }
    },
    "src/engine/match.ts::simulateUserFixture": {
      "metrics": { "statements": { "value": 77, "max": 50 } }
    }
  }
}
```

- 文件级指标（`lines`）以路径为实体。
- 具名函数指标以 `路径::函数名` 为实体；同名函数追加 `#2`。
- 无法提取名称的回调/匿名函数归入 `路径::<anonymous>`，按指标取最大值。
- `value` 是实测值，`max` 是当时配置的阈值；检查只比较 `value`，并要求技术债/重复率只能下降。

实际值由 `npm run quality:update` 生成，不手写。

## 棘轮规则

- 已有基线文件：修改后任一指标不得大于基线值。
- 基线文件被修改：只能持平、下降或删除条目。
- 新文件/新函数：直接按阈值卡。
- 函数重命名：需要显式更新基线，并在提交里带 `Baseline-Update:` 说明；不能借重命名抬高数值。
- 删除函数：`quality:update` 自动剪枝。
- CI 检查 baseline 文件 diff：没有 `Baseline-Update:` 就失败。

## 更新基线

```bash
npm run quality:update
```

脚本行为：

1. 重新扫描 `src/**` 与 `tests/**`。
2. 只保留仍超标的条目；已消失的条目自动删除。
3. 已有条目的数值只能下降；检测到上升就拒绝写入（保留旧值并退出非零）。
4. 新超标实体/指标不会自动加入基线；必须先拆分或申请人工评审。
5. 输出变更摘要，提醒是否需要 `Baseline-Update:`。

不要用“先调高基线再改代码”的方式绕过。确需调高时，必须人工改 JSON、在提交里解释原因，并让 reviewer 确认不可避免。

## 重复率

- 工具：`jscpd`，`minTokens: 70`。
- 按文件统计重复行数，存 `quality/duplication-baseline.json`。
- 已登记文件：重复行数不得增加。
- 新文件：重复率 ≤3%（测试 ≤5%）；可由 `quality:update` 纳入基线。
- 生成代码、测试 fixture、数据包可排除，但要在 `quality/jscpd.json` 里写明理由。

## 报告

```bash
npm run quality:report
```

输出：

- 总债务条目数、超标文件数。
- Top 10 大文件/高复杂度函数。
- 本次新增/恶化项。
- 覆盖率 floor 与当前值。
- 文档过期提醒。

开发前跑一次，提交前再跑一次。

## 偿还策略

优先级：

1. 高频修改的文件（看 `quality:file` 的最近提交）。
2. 复杂度最高、测试最薄弱的函数。
3. 阻碍模块边界的历史耦合（engine/world、llm/engine、platform/db）。
4. 纯行数大但结构清楚的文件可以延后。

每次触碰大文件时：

- 先加测试锁行为。
- 抽出一个纯函数或子模块。
- 更新基线（只降）。
- 提交里说明“无行为变化”或“行为变化 + 测试”。

## 例外

- 生成文件、数据包、第三方适配层可配置排除，但排除项要 review。
- 紧急修复可以暂时保留基线，但不能调高；后续补一个“还债”提交。
- 阈值调整必须写 ADR，并在 `docs/process/tech-debt.md` 更新表格。

## 反作弊

- `quality:update` 拒绝调高。
- baseline diff 需要 `Baseline-Update:`。
- CI 对比 base 分支，展示基线条目变化。
- review 重点看“为什么这个函数必须继续这么大”。
- 不把逻辑拆成无意义的碎片来骗行数；函数拆分要按职责，不是按行。
